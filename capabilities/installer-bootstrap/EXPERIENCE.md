# Installer experience

Automation owns the shared setup lifecycle, accessibility, and state projection. Each app owns its brand, packaging, prerequisites, configuration, permission decisions, and what the user can do after setup. The Media Delivery pilot opens from its existing launcher and requires a checkout and Python 3.11+. A self-contained first launch is a separate distribution milestone.

| Component | What the operator sees and can do | What the implementation must prove |
| --- | --- | --- |
| **Launch and fallback** | An explicit setup invocation opens one local browser screen. The terminal prints its address for a manual open. A separate headless command supports unattended use. | Platform launchers call the same adapter. A missing interpreter is handled before rendering, and a review or plan leaves the destination untouched. |
| **Opening scene** | One product mark, centered heading, short status line, and quiet layered backdrop. The heading and primary action remain readable at narrow widths. | Product identity remains legible without motion. A scene must never hide a decision, status, focus indicator, or recovery control. |
| **Review and destination** | Setup shows the actual target before Install. In the pilot, a different destination is supplied to the launcher. | Paths are real, local to the session, and rendered as text. Reviewing the plan does not create the target folder. |
| **Options** | Each toggle has a label, initial value, and concrete consequence. The pilot starts with **Prefer audio capture** off and **Check capture tools** on. Choices remain editable after a stopped or failed attempt. | GUI and headless use the same option IDs and typed values. Unknown values fail before work starts. A presentation-only motion toggle changes no install settings. |
| **Permission and policy decisions** | A future app must explain any account, elevation, agreement, default-app, import, or background behavior at the point of choice. | The consumer owns the permission and records its outcome. Consent is explicit for the side effect it authorizes. Exact placement and skip/defer behavior in the reference await local video review. |
| **Progress checklist** | Each row shows waiting, current, complete, skipped, needs attention, or failed in text and with a distinguishable marker. | Only the runner changes step state. A skipped step contributes zero progress and is excluded from the denominator. A warning reports completed work with a follow-up. A failure cannot advance that step. |
| **Progress rail and motion** | A lower rail carries one motion accent tied to real progress. The current step stays readable while the marker moves. The OS reduced-motion preference or the on-screen setting suppresses motion. | Percentage reflects completed selected steps, with no time-based estimates. A warning can coexist with 100% package progress. Art and motion remain secondary to the status and controls. |
| **Stop, failure, and retry** | Stop shows that the current step is finishing. A failed attempt keeps the failed row visible and preserves the chosen options for retry. | Later work is skipped after a stop. If publication already completed, setup reports the actual result. For the pilot, staged verification precedes atomic replacement, so failed publication leaves an earlier installation usable. |
| **Completion** | The final screen states what was installed and where. The pilot separately shows the capture-tools check as **Verified**, **Needs attention**, or **Not checked**, plus the command to run the installed dependency check. | Readiness reports only the declared check. A skipped probe cannot be shown as verified. The browser presents an inert command only after successful package publication. Successful setup does not prove a capture ran. |
| **First run and return** | App-specific launch, onboarding, skip/defer, and settings revisit belong here when supported. The pilot currently hands off via a local command. | Verify the exact launch, first usable screen, and state transitions on the target host. Record where a user can change a saved choice and what happens if they defer. |

## Reference reconciliation and desktop evidence

The supplied stills establish the visual treatment at 27% and 60%. Their checklist rows describe browser benefits. Use real installer phases for the pilot checklist. The stills leave the actual transition order, motion timing, default values, path to a skipped choice, and first-run sequence unknown.

Follow the [local video handoff](REFERENCE_VIDEO.md) for file-based review. For the full recording, capture one row per observed decision or transition. Record the timestamp range, screen, exact visible control or state, initial value, action, resulting effect, and visible back/skip/defer/revisit path. Mark fields the recording does not show as unknown. Keep footage, frames, and private locators in the authorized local handoff.

In a disposable Windows install directory, validate launch and fallback, unchanged destination before Install, option defaults and editing, one real progress transition, reduced-motion behavior, a stop or retry, and package publication. Then run the installed CLI from outside the checkout and record package success, prerequisite status, and first-run behavior independently. Attach sanitized observations to the exact candidate revision before marking the [release gates](release-gates.v1.json) complete.
